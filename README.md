# users

Микросервис приложения mood-bot: пользователи и их ответы на вопросы бота.

## Режимы запуска — один образ, три роли (Фактор 12)

```bash
users                  # долгоживущий HTTP-сервис
users migrate          # разовая задача: накатить миграции
users admin stats      # разовая задача: сводка по данным
users admin answers    # разовая задача: последние ответы
```

Административные команды живут в том же бинарнике намеренно. Отдельный скрипт
неизбежно отстаёт от кода, ходит в базу под другим пользователем и выполняется
на машине человека, а не в окружении приложения. Подкоманда получает ту же
конфигурацию из тех же переменных, тот же драйвер и ту же версию схемы.

```bash
# админ-команда в боевом окружении, без выдачи доступа к самой базе
kubectl -n moodbot exec deploy/users -- users admin stats
```

## Миграции

SQL-файлы встроены в бинарник через `embed` — они едут в том же образе,
что и код. Порядок применения — по числовой версии в имени файла.
Учёт — в таблице `schema_migrations`, каждая миграция применяется
в одной транзакции вместе с отметкой о применении.

Одновременный запуск защищён `pg_advisory_lock`: второй процесс ждёт
первого, а не портит схему.

```bash
make up          # локально: postgres + миграции + сервис
make test        # те же тесты, что в CI, против настоящего PostgreSQL
make parity      # версии backing service в compose/CI/кластере не разъехались
```

### Важно при внедрении на СУЩЕСТВУЮЩУЮ базу

Если схема уже создана вручную (как это было здесь до задания 10), таблицы
`schema_migrations` в базе нет, и первый запуск `users migrate` посчитает
**все** миграции непринятыми и попытается накатить их заново.

Здесь это прошло без последствий только потому, что `0001` целиком написана
через `CREATE TABLE IF NOT EXISTS`. С `ALTER TABLE ... ADD COLUMN` без
`IF NOT EXISTS` или с `INSERT` начальных данных всё сломалось бы.

Правильный приём называется **baseline**: перед первым запуском вручную
объявить уже применённые версии.

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
    version BIGINT PRIMARY KEY, name TEXT NOT NULL,
    applied_at TIMESTAMPTZ NOT NULL DEFAULT now());
INSERT INTO schema_migrations(version, name) VALUES (1, '0001_init.up.sql')
    ON CONFLICT DO NOTHING;
```

## Про схему: expand / contract

Миграция `0002` добавила колонку `notify_enabled`, которой пока **никто
не пользуется** — и это не недоделка, а приём.

Схема и код выкатываются разными релизами, поэтому изменение делится на две
фазы. **Expand:** добавить колонку с безопасным значением по умолчанию —
старый код её не замечает, новый уже может использовать. **Contract:** когда
весь код обновлён, убрать старое. Между фазами система работает в обоих
состояниях, и откат кода не требует отката схемы.

Обратный порядок («переименуем колонку одной миграцией») означает, что
в момент выкатки часть реплик работает со старым кодом и новой схемой —
то есть пятисотки ровно на время роллинга.

## Как это развёрнуто

Kubernetes, namespace `moodbot`: Deployment (HPA 2–8, PDB, три пробы,
`preStop`), Service, ConfigMap, Secret. Конвейер — `build → release → run`
с миграционным Job строго перед выкаткой кода.
Манифесты в [deploy/](deploy/), workflow в [.github/workflows/](.github/workflows/).
